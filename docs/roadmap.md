## Этап 1 (MVP) — Direct connection

Сделано вне порядка ТЗ (ветка `feat/setup-portal`): удержание BOOT 5 с поднимает
точку доступа настройки, вход администратора (PBKDF2, сессии, защита от перебора),
выбор режима Direct / Bastion (поиск Wi-Fi, проверка подключения, адрес бастиона),
хранение режима в NVS, машина состояний, индикация, сброс до заводских по 15 с.
Заводские пароли — из `firmware/.env`.

Ветка `feat/direct-console`: компонент `wcs_console` (UART, параметры линии, BREAK,
история в PSRAM), xterm.js во флеше, мост WebSocket ↔ UART по HTTPS, «Устройство занято»,
свои SSID и пароль Direct в мастере настройки. Осталось проверить на железе (пункт 1).

Не делаем: смену пароля администратора через веб-интерфейс — пароли задаются
в `firmware/.env` до сборки, в прошивку попадает только хэш.

1. [ ] Связка ESP → MAX3232 → консоль коммутатора: эхо UART через USB-порт ESP
2. [ ] Точка доступа, веб-сервер, xterm.js, мост WebSocket ↔ UART — сделано сразу по HTTPS, ждёт проверки на плате
3. [x] HTTPS с генерацией сертификата на устройстве (ECDSA P-256, хранится при сбросе до заводских; HTTP → HTTPS перенаправление)
4. [ ] Вход, сессии, хэши паролей, защита от перебора, «Устройство занято»
5. [ ] Веб-интерфейс настройки, хранение настроек в NVS
6. [ ] Машина состояний, кнопка, светодиод, закрытие настройки после выбора режима
7. [ ] Таймер выключения точки доступа, ограничение на одного клиента

## Бастион: безопасность и эксплуатация (план)

Идеи по итогам обзора аналогов (Opengear, JumpServer, Teleport). Всё только для режима бастиона. Порядок — по важности для защиты. Решили не делать: второй фактор, внешнюю аутентификацию (LDAP/OIDC) — слишком сложно для проекта. Сертификацию СКЗИ не получаем: цель — показать, что решение работает и быстрое.

1. [ ] Запись сессий консоли: полный ввод и вывод с метками времени, воспроизведение, защита журнала от подмены (цепочка хэшей), экспорт в syslog/SIEM, срок хранения
2. [ ] Оповещения: слова-триггеры в выводе консоли, устройство офлайн, всплеск неудачных входов, сброс по кнопке; доставка на email, syslog, Telegram
3. [ ] Фильтрация команд: опасные команды (`erase`, `reload`, `write erase`) по правилам — запрет, подтверждение или предупреждение; срабатывания в журнале
4. [ ] Временный доступ: выдачи прав на N часов, согласование (принцип «четырёх глаз») для опасных действий, аварийный вход (break-glass) с обязательным журналом
5. [ ] Завершение чужой сессии администратором
6. [ ] Резервное копирование и восстановление бастиона: ключ CA, БД, `data/`; контроль сроков и перевыпуск сертификатов
7. [ ] Сбор состояния оборудования через консоль: профили производителей (Cisco IOS, Huawei VRP, MikroTik, …), опрос по расписанию без помех людям, разбор `show`-команд, хранение метрик, эндпоинт `/metrics` для Prometheus
8. [ ] Выгрузка конфигураций одной командой (веб и SSH-шлюз), версии и diff, проверка на соответствие эталону (аудит настроек: telnet, SNMP v1/v2, пароли открытым текстом и т.п.)
9. [ ] Замеры производительности: задержка от нажатия до эха (Direct и бастион), пропускная способность на 115200, время подключения и переподключения, загрузка CPU и память ESP, нагрузка на бастион при сотнях тестовых устройств (`mix bastion.device`)
10. [ ] Границы применимости и соответствие требованиям: таблица «мера → реализация → проверка» по группам мер ФСТЭК, модель угроз, что нужно для применения в сетях с повышенными требованиями (сертифицированные СКЗИ, вопрос беспроводного канала) — `docs/compliance.md`
